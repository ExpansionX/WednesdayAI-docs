# Context Window & Compaction

Every model has a **context window** (max tokens it can see). Long-running chats accumulate messages and tool results; once the window is tight, WednesdayAI **compacts** older history to stay within limits.

## What compaction is

Compaction **summarizes older conversation** into a compact summary entry and keeps recent messages intact. The summary is stored in the session history, so future requests use:

- The compaction summary
- Recent messages after the compaction point

Compaction **appends** its summary to SQL session history; it does not rewrite or delete earlier entries.

## Configuration

Use the `agents.defaults.compaction` object in your `openclaw.json` to control compaction behavior.

### Summarizer model

Core compaction summarizes with the session's own model — the provider and model the run uses.
There is no built-in fallback model: when no provider/model can be resolved for the session,
compaction fails with `compaction skipped: no provider/model resolved` (recorded in the
compaction diagnostics row) rather than silently substituting a default. If you hit this, set
`agents.defaults.model` so the session has an active model.

### Examples

Disable compaction entirely:

```json5
{
  agents: {
    defaults: {
      compaction: { enabled: false },
    },
  },
}
```

Switch identifier preservation off:

```json5
{
  agents: {
    defaults: {
      compaction: { identifierPolicy: "off" },
    },
  },
}
```

Provide custom identifier preservation instructions:

```json5
{
  agents: {
    defaults: {
      compaction: {
        identifierPolicy: "custom",
        identifierInstructions: "Preserve all ticket IDs (e.g. PROJ-1234) and branch names exactly as written.",
      },
    },
  },
}
```

## Auto-compaction (default on)

When a session nears or exceeds the model’s context window, WednesdayAI triggers auto-compaction and may retry the original request using the compacted context.

You’ll see:

- `🧹 Auto-compaction complete` in verbose mode
- `/status` showing `🧹 Compactions: <count>`

### Who recovers a context overflow

When compaction is enabled, an eligible embedded agent run hands a just-streamed
**same-model context-overflow error** (the model reports the prompt exceeded its own
window) to WednesdayAI's run loop: pi's own overflow branch is cancelled, and the run loop
runs core compaction (recorded in the compaction ledger) and schedules background
summary-DAG production, then retries the prompt.

The handoff is not registered for `analysis` runs, runs without a session file, or runs
with `disablePluginHooks`, `skipTranscriptSync`, or `suppressTranscriptPersistence`. Those
runs recover inside pi and write no compaction-ledger row.

Two pi-internal compactions keep running inside the attempt when compaction is enabled:
pi's **threshold** auto-compaction (context nearing the window after a turn) and pi's
**pre-prompt preflight** (compacting a previous turn's unresolved overflow before the new
prompt is sent). Neither writes the compaction ledger; the run-loop overflow recovery
does.

With `enabled: false`, none of these run: core compaction refuses (the run surfaces the
overflow as a turn error instead of retrying) and pi's internal auto-compaction is
switched off through its settings.

Before compaction, WednesdayAI can run a **silent memory flush** turn to store
durable notes to disk. See [Memory](/next/developers/concepts/memory) for details and config.

The memory-flush size check reads a stored byte total and the latest usable token
usage from SQL, rather than loading the transcript into the agent process. The first
check aggregates existing rows; later checks aggregate only newly appended rows.
Existing history contributes immediately after an upgrade, without waiting for
background token-column backfills. Entries with no usable prompt or output usage
do not hide the last usable usage record.
`memoryFlush.forceFlushTranscriptBytes` measures serialized UTF-8 bytes, including
one newline per entry, without changing the configured threshold behavior.

## Manual compaction

Use `/compact` (optionally with instructions) to force a compaction pass:

```
/compact Focus on decisions and open questions
```

## Compaction ownership

Sessions claimed by a **compaction-stage context owner** suppress core compaction: the owner's
`session_before_compact` hook cancels SDK auto-compaction (including run-loop overflow recovery)
and core `/compact` for the claimed session, so the owner — not WednesdayAI — decides when and how
history is compacted.

For operators:

- Do not expect `🧹 Auto-compaction complete` or the `/compact` command to fire on sessions owned
  by a compaction-stage owner. The owner is responsible for keeping that session under its window.
- A claimed session can still hit its context window if the owner never compacts; monitor owned
  sessions through the owner's own reporting rather than WednesdayAI's compaction counters.
- Unclaimed (core-owned) sessions behave exactly as described in the sections above.

## Summary-DAG per-turn trigger

Independent of who owns compaction, every successful turn schedules a background
summary-DAG production (the leaf summaries over the session history's uncovered span). The
reply never waits on it and never fails from it; a prune veto or a compaction-stage owner
does not suppress it, and compaction-triggered production is fire-and-forget too — compaction
schedules it and moves on. Heartbeat runs skip the turn trigger. Turn it off per agent with
`agents.list[].summaryDag.turnTrigger: false` (default `true`), or globally with
`agents.defaults.compaction.summaryDag.turnTrigger: false`.

### Which model summarizes

Each production resolves its summarizer in this order and logs
`summary-DAG summarizer: <label> (source: config|session|stored)` once per production run:

1. `summaryDag.model` (`source: config`) — the dedicated summarizer, as `"provider/modelId"`.
2. The session's active model (`source: session`).
3. The last model stored on the session rows — `source: stored`, backfill only.

When none of the three resolves, production is skipped for that trigger and the uncovered
span stays raw until a later production covers it. A configured but unresolvable model does
not silently swap to a later tier: resolution stops there and production skips.

### What the summary-DAG summarizer never sees

Leaf planning runs ingest hygiene on the planning view only — stored session rows are
never modified. Before spans are planned:

- **Heartbeat entries** (`trigger_source='heartbeat'`) are dropped from the summarizer
  input entirely — heartbeat runs exist to keep a session alive, and their ticks and
  alerts are not conversation worth summarizing. The legacy hidden-ack marker
  (`openclaw:heartbeat-hidden`) still drops ack exchanges from runs that predate the
  column. Heartbeat entries also never count toward the protected fresh tail.
- **Injected context** on user rows (memory recall and similar) is stripped.
- **Byte-identical replays** of a message inside the same planning input are dropped.
- **Oversized tool payloads** (over `summaryDag.toolPayloadStubTokens`, default `25000`,
  clamped to the leaf chunk budget) are replaced by a short stub line
  (`[tool payload stubbed: tool=… | N bytes | seq …]`) plus the configured head
  (`summaryDag.toolPayloadStubHeadChars`, default `500`); the full payload stays
  recoverable from the session log by seq. An oversize user/assistant message is never
  stubbed — the planner stops before it instead.

Batches written under these rules are marked `planner: "rendered-v2"` in their metadata,
so a future recovery can tell them apart from older batches. Every `summaryDag.*` sizing
key (chunk budget, fanouts, sweep caps, fresh tail, narration targets, advisor deadline)
is documented in [Gateway configuration reference](/next/admin/gateway/configuration-reference).

## Context window source

Context window is model-specific. WednesdayAI uses the model definition from the configured provider catalog to determine limits.

## Compaction vs pruning

- **Compaction**: summarises and **appends** the summary to SQL history.
- **Session pruning**: trims old **tool results** only, **in-memory**, per request.

See [/concepts/session-pruning](/next/developers/concepts/session-pruning) for pruning details.

## OpenAI server-side compaction

WednesdayAI also supports OpenAI Responses server-side compaction hints for
compatible direct OpenAI models. This is separate from local WednesdayAI
compaction and can run alongside it.

- Local compaction: WednesdayAI summarizes and appends the summary to SQL session history.
- Server-side compaction: OpenAI compacts context on the provider side when
  `store` + `context_management` are enabled.

See [OpenAI provider](/next/admin/providers/openai) for model params and overrides.

## Tool output is capped before it accumulates

Tool results are capped **in memory** at `400,000` text characters at the tool seam and again
when a session hydrates from storage. Oversized results keep a head-and-tail excerpt plus a size
note. When database write-through is enabled, the full raw bytes are stored out-of-band, so the
storage layer still holds the original output even though the model view is capped. Long sessions
do not accumulate multi-megabyte tool output in memory.

If a prune or compaction decision cannot be replayed from its stored ledger row, the session logs
`prompt ledger unavailable; recomputing projections` and repairs itself by recomputing the
projection from stored history. This is a one-time, self-repairing warning — not a data loss.

## Tips

- Use `/compact` when sessions feel stale or context is bloated.
- Large tool outputs are already truncated (tool results are capped at 400k chars in memory);
  pruning can further reduce tool-result buildup in the request view.
- If you need a fresh slate, `/new` or `/reset` starts a new session id.

## Troubleshooting

**Compaction triggers but the session still hits context limits**
The summary may be larger than expected, or recent messages alone already exceed the window. Check your `keepRecentTokens` and `reserveTokens` settings. If recent messages are unavoidably large (for example, huge tool outputs), combine compaction with session pruning (`contextPruning`) to trim tool results before the LLM call.

**Identifier (ticket ID, branch name) lost after compaction**
The default `identifierPolicy: "strict"` adds built-in guidance, but identifiers buried deep in tool output may not survive. Switch to `"custom"` and provide explicit `identifierInstructions` naming the identifier patterns you care about (for example `"Preserve all PROJ-* ticket IDs exactly"`). Confirm with `/compact Focus on ticket IDs and branch names`.

**`enabled: false` still seems to compact**
`enabled: false` stops core compaction and pi's internal auto-compaction alike; what it
does **not** stop is compaction performed by a compaction-stage context owner plugin, and
the summary-DAG per-turn trigger (which produces summaries without compacting). Config is
read at gateway start — restart the gateway after changing `compaction.enabled`, and
verify the config is under `agents.defaults.compaction`, not a top-level key.

**Memory flush runs unexpectedly or too often**
The flush fires when serialized conversation entries in SQL reach `memoryFlush.forceFlushTranscriptBytes`. Set it to `0` to disable size-based triggers, or increase the value. Set `memoryFlush.enabled: false` to turn off pre-compaction memory flushes entirely.
