# `wednesdayai inbox`

Query the local inbox message store — the unified, per-source replica of external messages
(Gmail via the `gog` watch pipeline, BlueBubbles (iMessage), Discord, WhatsApp, and Microsoft
365 mailboxes added as accounts by the agent; BlueBubbles
and Discord also backfill history through pull scanners while the gateway runs, and WhatsApp
feeds the store live from its inbox-mode account — see
[Account mode](/next/admin/channels/channel-routing#account-mode)).

`list` and `correct` read the store directly from disk; the gateway does not need to be
running. `backfill --source whatsapp` fetches history from the linked phone through the
running gateway.

## Usage

```bash
wednesdayai inbox list [--source <source>] [--direction in|out] [--account <accountId>] [--category <name>] [--review] [--since <when>] [--limit <n>]
wednesdayai inbox classifications [--since <when>] [--source <source>] [--account <accountId>] [--limit <n>] [--json]
wednesdayai inbox correct <id> <category>
wednesdayai inbox presets revert --migration <id>
wednesdayai inbox prefilter-score [--source <source>] [--since <iso>] [--min-precision <ratio>] [--min-support <n>] [--json]
wednesdayai inbox ms365 accounts list|add <account> --owner <person>|signin <account>|status [<account>]|remove <account> [--json]
wednesdayai inbox backfill --source <source> [--account <id>] [--since <iso> | --all | --convert]
wednesdayai inbox owners list [--json]
wednesdayai inbox owners bind <identity> <source:accountId>...
wednesdayai inbox owners unbind <source:accountId>...
```

## Flags

| Flag                      | Effect                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `--source <source>`       | Filter by source (e.g. `gmail`).                                                                                   |
| `--direction <direction>` | Filter by direction: `in` or `out`.                                                                                |
| `--account <accountId>`   | Filter by account id (e.g. `me@example.com`).                                                                      |
| `--category <name>`       | Only items with this category (e.g. `FYI`).                                                                        |
| `--review`                | Only the review queue: category `Unclear` or any policy flag.                                                      |
| `--since <when>`          | Only items whose message time is at or after `<when>`: a duration back from now (`24h`, `7d`) or an ISO timestamp. |
| `--limit <n>`             | Maximum rows to return (positive integer; the store defaults to 200).                                              |

Rows render as a table with id, source, direction, category, how the category was set,
policy flag, sender, subject, preview, and the source event timestamp (ms epoch). Newest
first. The category column shows `(pending)` for an item not classified yet and
`(skipped-history)` for history outside the account's [history policy](#history). The `By`
column is `model` for a model verdict, `prefilter:<signal>`, `manual` or `policy`. By
default, `inbox list` excludes archived items and items the source has deleted (tombstoned
in the store; the inbox never erases rows).

`inbox classifications` lists recent verdicts, newest first: when each item was classified,
its source and account, category, how it was set, the model (`<provider>/<model>`), policy
flag, sender and subject. `--since` defaults to `24h` and `--limit` to 200; `--json` prints
an array of `{ id, source, accountId, category, categorySource, categorySignal, policyFlag,
model, classifiedAt, ts, sender, subject }`. Items classified by builds before this field
existed have no classification time and do not appear.

`inbox backfill` pulls older history from a source into the store; `--convert` instead
re-renders stored gmail/ms365 rows whose body predates markdown rendering, from stored data
with no source fetch. Flags, checkpoints and per-source behaviour are in
[Inbox API](https://docs.wednesdayai.dev/developers/reference/inbox-api#backfill).
A precondition or fetch failure — source not enabled, source not configured, unknown source,
an account not in inbox mode (channel-backed sources report
`account "<ch>:<id>" is not in inbox mode`; dedicated sources report
`account not enabled for the source`), invalid `--since`, or a missing transport — prints one
line to stderr with no stack trace and exits with status 1 (for example,
`inbox source bluebubbles is not enabled`); committed pages stay checkpointed for the next run.

## `ms365 accounts`

```bash
wednesdayai inbox ms365 accounts list [--json]
wednesdayai inbox ms365 accounts add <account> --owner <person> [--json]
wednesdayai inbox ms365 accounts signin <account> [--json]
wednesdayai inbox ms365 accounts status [<account>] [--json]
wednesdayai inbox ms365 accounts remove <account> [--json]
```

Manages the Microsoft 365 accounts of this deployment: several mailboxes, one slot label
each, stored in the inbox database. `<account>` is a slot label — lowercase letters, digits
and hyphen, at most 32 characters, starting with a letter or digit. See
[Microsoft 365 inbox source](/next/developers/reference/inbox-ms365#4-add-sign-in-and-remove-accounts) for
the Entra app setup and the account model. These commands talk to the **running gateway**
(unlike `list` and `correct`, which read the store directly); start the gateway first.

- `list` renders one row per account with five columns: account (slot label), state,
  username, owner and failure reason. Without an argument, `status` prints the same table.
- `add` registers a new slot and starts its device-code sign-in. `--owner` names the person
  the account belongs to (an existing identity name, as with `owners bind`). The name is
  matched case-insensitively and stored as the configured identity key; an unknown name is
  refused with `unknown-owner` and nothing is written. The owner binding for mail and
  calendar is written with the account, before any mail is ingested.
- `signin` starts (or restarts) the device-code sign-in for the slot. It prints the
  verification URL and the code, then polls the account status every 5 seconds until the
  account is `active`, signed out again, or the code expired. Ctrl-C ends the polling
  without affecting the sign-in. A re-consent of an already signed-in account (for example
  after adding `Calendars.Read` to `inbox.ms365.scopes`) polls until its flow completes.
  `add` and `signin` exit 0 only when the account ends `active`; any other end state, a
  refusal, or (with `--json`) a non-ok outcome exits 1. With `--json`, stdout is one JSON
  document — the call's outcome, including the device code — and the command then waits
  silently for the same end state. Without `--json`, an already-pending sign-in whose code
  has arrived is not a refusal: the command prints that code and polls as above.
- `status <account>` reports one account. The rendered table shows the same five columns
  as `list` — the pending device-code URL, code and expiry are NOT printed there; use
  `status <account> --json` to read them from the view's `pendingSignin` field.
- `remove` stops syncing the slot and deletes its stored sign-in. Mail already ingested is
  kept, and the slot can be re-added later by signing in as the same identity.

`add` and `signin` require the `inbox.ms365.clientId` config key. In app-only mode, `signin`
runs no device code: it re-verifies the configured mailbox with the configured client
secret.

Sign-in always starts from an operator: these commands, the Control UI (**Channels →
Microsoft 365** panel), or the approval-gated `inbox.ms365_accounts` agent tool. The gateway
never starts one in the background. While an account is signed out it makes no calls to
Microsoft and sends one nudge per episode.

### `ms365 login` (deprecated)

```bash
wednesdayai inbox ms365 login
```

Deprecated alias for `inbox ms365 accounts signin <legacy account>`, where the legacy
account is the single mailbox this deployment used before accounts moved into the inbox
database (the `inbox.ms365.mailbox` slot when set, otherwise `default`). It prints
`inbox ms365 login is deprecated; use: wednesdayai inbox ms365 accounts signin <account>`
and then behaves like `signin`.

## `owners`

```bash
wednesdayai inbox owners list [--json]
wednesdayai inbox owners bind <identity> <source:accountId>...
wednesdayai inbox owners unbind <source:accountId>...
```

Lists, binds and unbinds which person owns each inbox account. An account has at most one
owner; `<identity>` is an existing `session.identityLinks` key (create one with
`wednesdayai identity add <name>`) and an account is written as `<source>:<accountId>` (for
example `ms365:default`). Binding an account to a person removes it from any previous owner,
and both commands take effect immediately — no gateway restart. Requires admin scope.

`list` renders every connected `source:accountId` with its owner (`—` when unbound) and, when
anything is unbound, a footer naming the `bind` command. A `Config` column appears only when
an `inbox.owners` config entry differs from the stored owner (`—` when null); `--json` prints
the raw result.

`bind` prints `Bound <entry> to <identity>.` per account, with ` (moved from <previous>)` when
it changed hands and `<entry> already bound to <identity>.` otherwise; `unbind` prints
`Unbound <entry> from <person>.`, or `<entry> was not bound.` Unbind deletes the stored
binding.

The web client's Inbox names this command when a signed-in person has no accounts bound.

## `digest-gate`

```bash
wednesdayai inbox digest-gate
```

The heartbeat **wakeGate** command: a cheap check that wakes the agent only when a digest
candidate exists. Wire it as a command-kind gate:

```json5
{
  agents: {
    defaults: {
      heartbeat: {
        wakeGate: { kind: "command", command: "wednesdayai inbox digest-gate" },
      },
    },
  },
}
```

The **last stdout line** is the JSON payload (all diagnostics go to stderr):

- `{"wakeAgent":false}` — nothing actionable; the heartbeat stays silent.
- `{"wakeAgent":true,"text":"...","data":{"candidateCursor":"<ts>:<id>"}}` — a digest of the
  eligible items. `text` is sender-controlled content wrapped as untrusted context, so it is
  never rendered as trusted gateway text.

Eligible items are inbound rows in the digest categories (`Notification`, `To Read` on email
and `Transactions` on chat, ADR 2734) with no policy flag, newer than the stored cursor. A
fresh uncategorized row inside the 30-minute settlement grace clamps the digest so a
soon-to-be-classified item is never double-surfaced.

The command is **read-only against the main cursor**: it never advances
`inbox_cursors(source='digest', scope='heartbeat')`. On a wake it durably writes the candidate
to the `heartbeat_pending` scope, and the inbox plugin advances the main cursor only when the
heartbeat outcome was actually delivered (`sent` / `ok-empty` / `ok-token`); `failed` and
`skipped` outcomes clear the pending candidate so the next run re-includes the same items.
Oversized digests are item-capped and the cursor clamps to the last rendered item, so the
backlog drains over consecutive heartbeats instead of overflowing the gate's output budget.

Related nudge tiers (no CLI surface): operator matchers under `inbox.urgent[]` nudge the
agent's main session for urgent items, and remaining actionable items surface as one-line
system events on the next user turn. See the config schema help for `inbox.urgent`.

## Urgent rules

`inbox.urgent` is a list of matchers; a matching **inbound** item nudges the agent's main
session exactly once (durable dedupe). Rules OR — one match is enough; within one rule every
set field must match:

```json5
{
  inbox: {
    urgent: [
      { from: "alice@x.com" }, // case-insensitive substring on the sender
      { source: "gmail", subjectIncludes: "invoice" }, // source exact; subject substring
      { label: "IMPORTANT" }, // source-native label membership
    ],
  },
}
```

An empty list (the default) stays silent. A nudge that fails to enqueue recovers through the
next-turn FYI surface; a denied grant never surfaces (grant-policy silence). Mutating mailbox
actions stay behind `plugins.entries.inbox.grants.inbox.actions` and operator approval — the
nudge tiers themselves never send anything.

## Classification

Inbound items are classified on ingest through the analysis runtime; `inbox.classify` selects
the provider/model and the output budget:

```json5
{
  inbox: {
    classify: {
      provider: "bifrost", // default
      // model: "…", // explicit override — wins over both tiers
      smallModel: "low", // default; prompts under tierThresholdChars
      mediumModel: "medium", // default; prompts at or over the threshold
      tierThresholdChars: 32768, // explicit boundary; default derives from the small model's contextWindow
      // maxOutputTokens: 2048, // explicit budget — wins over the vocabulary rule
    },
  },
}
```

- Prompts shorter than the tier threshold use `smallModel` (default `"low"`); prompts at or
  over it use `mediumModel` (default `"medium"`). An explicit `model` overrides both tiers.
  The threshold is `tierThresholdChars` when set. Otherwise, when `models.providers` declares
  the small model with a `contextWindow`, it is `(contextWindow - 2048) * 2` chars (28 672
  for a 16k window); else 32 768.
- A classify model that `models.providers` declares no entry for on its provider is reported
  by `wednesdayai doctor` and logged at gateway start. Nothing is rerouted: items routed to it
  stay pending.
- The classifier prompt carries sender, subject and, for gmail/ms365 rows with a rendered
  body, a markdown excerpt of the body: images become their alt text, `data:` URIs are
  dropped, link targets longer than 80 characters shrink to their hostname, and bare and
  `<…>` URLs longer than 80 characters shrink to their hostname; the compacted body keeps
  its first 3,000 and last 1,000 characters when it is longer than 4,000. Bodies whose
  compacted text is empty use the preview, as do other rows.
- The output budget defaults to the enabled-rule vocabulary:
  `max(longest enabled rule name + 256, 1024)` tokens, so a verdict always fits in one
  response. An explicit `maxOutputTokens` wins.
- A verdict cut off by the provider's length stop is never coerced to `Unclear` /
  `low-confidence`: the item keeps `category = NULL`, is flagged `classify-truncated`, and
  the retry sweep re-attempts it. Databases created before the flag existed are migrated on
  first open (#2251), so the flag write succeeds there too.

See the config schema help for `inbox.classify`.

### History

Linking an account backfills its history, and by default none of it is classified. An
inbound item is classified only when its message time is at or after the moment the inbox
first ingested anything for its account, minus a 10-minute grace. Older rows stay
unclassified at no cost and show as `(skipped-history)` in `inbox list` and
"History, not classified" in the web inbox.

Opt in per account (`"<source>:<accountId>"`), per source (`"<source>"`), or for every
account (`default`); the account key wins over the source key, which wins over the default:

```json5
{
  inbox: {
    classify: {
      history: {
        default: { mode: "live" }, // the built-in default
        accounts: {
          "ms365:default": { mode: "window", days: 30 }, // also the last 30 days
          gmail: { mode: "all" }, // every gmail account, all history
        },
      },
    },
  },
}
```

- `live`: only items sent after the account was linked.
- `window`: also items from the last `days` days. `days` is required with `window` and
  rejected with any other mode.
- `all`: every stored item.

The policy is applied at the start of every sweep pass. Widening it moves the newly covered
rows back to pending, and the sweep classifies them on that and later passes; narrowing it
parks unclassified rows again. Rows that already have a category are never touched.
`wednesdayai doctor` prints each account's policy with its pending, skipped-history and done
counts.

### Retry sweep

Items that stay unclassified (a failed or rejected classification, or history inside the
account's history policy, which is never classified at ingest) are re-attempted by a
background sweep every 5 minutes, once they are at least 1 minute old:

- The sweep walks the newest messages first (by message time), so live mail is never
  queued behind a historic backlog.
- It keeps at most 2 classifications queued or running, leaving the rest of the plugin's 4
  background analysis slots to live classification. A pass stops starting work after 4
  minutes, so the next pass begins again at the newest message.
- Each item gets at most 5 attempts per gateway run. After an attempt finishes without a
  category (a failed run, an `empty` result, or a refusal), the item waits 5 minutes, then
  10, 20 and 40, counted from when that attempt finished, so an attempt never repeats on the
  next pass. When the analysis queue is full the sweep waits for a free slot and spends no
  attempt; a job the runtime refuses for that item spends one. Attempt state is dropped once
  the item is classified or deleted, and deleted messages are never swept.
- A live item the analysis queue refuses is logged
  (`classify-on-ingest: analysis queue rejected … (<reason>)`) and waits for the sweep. Each
  pass logs one summary line: `pass enqueued N, prefiltered N, rejected N, queue-full waits N,
ended: drained|budget|stopped|error`, and one line per account whose rows the history policy
  moved: `classify history: <source>:<accountId> policy <mode> marked N skipped-history,
  restored N pending`.

### Prefilter

Before the LLM call, a deterministic pre-classifier (the "prefilter", ADR 2443) evaluates
structural signals computed from the stored row only. `inbox.classify.prefilter` selects the
mode:

- `off` — the prefilter is skipped entirely.
- `shadow` (default) — prefilter verdicts are computed and logged for tuning, but every item
  is still classified by the LLM.
- `on` — a matching structural signal (calendar invite, bounce, auto-reply, tool
  notification, Gmail Promotions, Discord bot) or a consistent sender history sets the
  category without an LLM call. The result is stored with `category_source='prefilter'` and
  the matched signal in `category_signal`.

| Signal              | Verdict                                                                    |
| ------------------- | -------------------------------------------------------------------------- |
| `imip`              | `Meetings` (email rows) / `FYI` (chat rows)                                |
| `delivery-report`   | `Notification`                                                             |
| `mailer-daemon`     | `Notification`                                                             |
| `auto-replied`      | `To Read` (email rows) / `FYI` (chat rows)                                 |
| `auto-generated`    | `Notification`                                                             |
| `tool-notification` | `Notification`                                                             |
| `discord-bot`       | `Transactions`                                                             |
| `gmail-promotions`  | `Sales & Marketing`                                                        |
| `sender-memory`     | the sender's prior verdict                                                 |
| `bulk`              | no category — removes `To Respond` / `Needs Reply` from the LLM vocabulary |

The prefilter is conservative by design:

- An enabled user or correction-learned rule **gates** the signals it could collide with:
  its condition is prose that may claim any message, so every structural signal (`imip`
  through `gmail-promotions`) stops short-circuiting while it is enabled. The `bulk` hint
  is gated only by a custom rule named `To Respond` or `Needs Reply`. `sender-memory` is never gated: it
  replays the sender's own earlier verdicts, which were made with the custom rules in the
  prompt. Gated signals are still shadow-logged; the gateway logs one warning naming them,
  and `wednesdayai doctor` lists them.
- It **never overwrites** a non-NULL category, so a manually corrected item stays manual.
- `sender-memory` replays a sender's earlier verdicts only when they are unanimous (≥ 3
  verdicts, one category) and never replays `To Respond`, `Needs Reply`, `Awaiting Reply` or
  `Unclear`.
- In `on` mode, `inbox.classify.prefilterSignals` allowlists which signals may
  short-circuit (unset = all). Add a signal only after `inbox prefilter-score` reports
  PASS for it — the bar is precision ≥ 0.8 over ≥ 50 scored rows.

### First pass

After the prefilter declines and before the full classifier, `inbox.classify.firstPass`
(ADR 2734) runs one small JSON call asking whether the message is an automated notification
or transactional message sent by a system rather than written by a person. The row's preset
scope decides which category a `true` verdict writes: `Notification` for email rows,
`Transactions` for chat rows, stored with `category_source='rule'` and
`category_signal='first-pass'` — and the full classifier call is skipped.

- `off` — the probe is skipped entirely.
- `shadow` (default) — the probe runs, the full classifier still owns the write, and the
  agreement between the two is logged: `first-pass shadow: item <id> notification <bool> llm
<verdict> agree|disagree`.
- `on` — a `true` verdict writes the notification rule directly. Anything else — `false`,
  unparseable output, or any non-ok result — falls through to the full classifier, so an
  unavailable model still surfaces as unavailable.

The probe costs no extra attempt: the retry sweep still counts one admitted attempt per
item, with the full call chained behind the probe's completion. A refused chained call
leaves the item pending for the sweep. The prompt vocabulary itself is scoped per row:
email rows see the email preset rules, chat rows the chat preset ones (ADR 2734 §1), and
the prompt carries the row's source, chat kind, group title and owner-addressing level
inside the data fence.

Data limits: Gmail watch-push rows carry no message headers, so header-based signals fire
only for full-fetched Gmail rows. A Gmail reconcile pass adds the headers to the watch rows
whose history it replays, and `inbox backfill --source gmail --all` adds them to every
stored row. ms365 rows keep an allowlisted subset of the `internetMessageHeaders` that
`MS365_MESSAGE_SELECT` requests. A `List-Id` header alone is never a signal.

## Scoring prefilter signals: `inbox prefilter-score`

```bash
wednesdayai inbox prefilter-score [--source <source>] [--since <iso>]
                                  [--min-precision <ratio>] [--min-support <n>] [--json]
```

Scores every prefilter signal offline against the verdicts already in the store: it replays
each signal over inbound history and compares the signal's fixed verdict with the truth on
each row (an LLM `rule` verdict or a `manual` correction; `low-confidence` rows and other
prefilter rows are never truth). Use it to decide which signals meet the enablement bar
before turning the prefilter on.

| Flag                      | Effect                                                              |
| ------------------------- | ------------------------------------------------------------------- |
| `--source <source>`       | Score one source only (e.g. `gmail`).                               |
| `--since <iso>`           | Only rows at or after this time.                                    |
| `--min-precision <ratio>` | Minimum precision for a signal to PASS (default 0.8; range (0, 1]). |
| `--min-support <n>`       | Minimum scored rows for a signal to PASS (default 50).              |
| `--json`                  | Print the report as one JSON line on stdout.                        |

The output is one row per signal:

- how often it fired;
- how many rows are **evaluable**, meaning they carry the evidence the signal reads;
- how many fired rows carry a truth, and how many of those agree;
- the precision (two decimals, `-` when nothing was scored);
- the **recall**: agreeing fires divided by the evaluable truth rows of the signal's
  verdict (`-` when there are none);
- the manual agreement (`agree/scored`);
- the most common disagreeing category;
- PASS or FAIL against `--min-precision` over `--min-support` scored rows. Recall does not
  affect the result.

A signal with 0 evaluable rows has no data to read; its 0 fires are not proof that the
messages are absent. A signal with evaluable rows and 0 fires never fired on that data.
For `bulk`, the verdict class is any category except `To Respond` / `Needs Reply`.
For `sender-memory`, it is any category that memory can replay.

`--json` adds `evaluable`, `notEvaluable`, `recallBase`, and `recall` to each signal.

When an enabled custom rule gates an active signal, the text output ends with one line per
gated signal, for example `Gated (won't short-circuit in on mode): imip by Invoices`, and
`--json` lists them under `gates` (`[{ "signal": "imip", "rules": ["Invoices"] }]`).

To add headers to rows stored before a source persisted them, run
`wednesdayai inbox backfill --source ms365 --all` (or `--source gmail --all`). A re-fetch
adds missing evidence fields to `raw_json` and never replaces a stored value.

`sender-memory` replays only each row's earlier history. Corrections are applied **as of
now**, not as of each row's time. This is an approximation, because `correctedFrom`
reflects today's corrections.

Like `inbox list`, the command opens the store directly from disk, so it applies pending
schema migrations on open and never needs the gateway running.

## Reclassifying an item: `inbox correct`

```bash
wednesdayai inbox correct <id> <category>
```

Manually reclassify one stored item (id as shown by `inbox list`). `<category>` must be an
**enabled** inbox rule name; it is validated against the enabled rules before anything is
written. On success the command prints `Corrected <id> → <category>` and the correction:

- appends a row to `inbox_corrections` — the retrain signal: recent corrections are carried
  in the next classification prompts for similar items, inside a fence that marks the corrected
  item's sender, subject and preview as data rather than instructions,
- flips the item to the new category with `category_source='manual'`, and clears any
  `policy_flag` (the item leaves the review queue).

Errors are loud and write nothing: an unknown item id fails with
`no inbox item with id "<id>"`; an unknown or disabled category fails before any write —
the item is unchanged and no correction row is written.

## Reverting a category migration: `inbox presets revert`

```bash
wednesdayai inbox presets revert --migration d2-presets-v1
```

The D2 category presets (ADR 2734) remapped existing rows once, on the first store open: old
starter categories moved to the preset names (`Newsletter` → `To Read` on email, `FYI` on
chat; `Marketing/Cold` → `Sales & Marketing` / `Promotions`; `Receipts/Finance` →
`Invoices & Receipts` / `Transactions`; `Notifications` → `Notification` / `Transactions`;
`Calendar/Meeting` → `Meetings` / `FYI`; `Needs Reply` → `To Respond` on email), old starter
rules outside the presets were disabled, `Travel` became a user rule, and thread reply states
were recomputed. Every original value was logged before it changed.

`presets revert` undoes that migration in one transaction and prints the restored counts
(`N items, N rules, N threads restored`). It restores only values the migration itself
wrote: an item recategorized after the remap keeps its newer category, and log rows are
never deleted. A `__reverted__` marker keeps the next store open from re-applying the
migration. Email rows are `gmail`/`ms365`; every other source is chat.

## Storage configuration

The store location follows `session.storage` unless overridden under `inbox.storage`
(same driver, separate database — inbox data never shares the session database):

```json5
{
  inbox: {
    storage: {
      backend: "sqlite", // "sqlite" (default) or "postgres"
      sqlitePath: "/var/lib/wednesdayai/inbox.sqlite", // default: <stateDir>/inbox.sqlite
      // databaseUrl: "postgres://…", // required when backend is "postgres" (or OPENCLAW_INBOX_DATABASE_URL)
      sqlite: {
        wal: true, // default: on
        busyTimeoutMs: 5000, // default: 5000
        walAutocheckpointPages: 1000, // default: 1000
      },
    },
  },
}
```

Notes:

- `inbox.storage.databaseUrl` is treated as a sensitive config value (redacted from
  diagnostics).
- A postgres `databaseUrl` pointing at the session storage database is rejected — the inbox
  requires its own database.
- The SQLite database file is created `0600`; a custom `sqlitePath` may point into a
  directory that does not exist yet (it is created).
