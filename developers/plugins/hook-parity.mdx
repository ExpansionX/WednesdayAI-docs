# Hook parity with upstream openclaw

WednesdayAI is a fork of upstream openclaw, and the plugin hook surface has drifted between
the two. This page is the map. It pins the upstream reference level: openclaw `v2026.6.9`
(commit `c645ec4`), taken from the `PLUGIN_HOOK_NAMES` array in upstream
`src/plugins/hook-types.ts`.

Every upstream hook name has one of three statuses:

- `both` — the hook exists in upstream openclaw and WednesdayAI dispatches it. Register it
  with `api.on` and it works in both.
- `upstream only` — the hook exists upstream but WednesdayAI does not dispatch it. Each row
  carries a disposition (below) and, where one exists, the WednesdayAI hook to use instead.
- `WednesdayAI only` — the hook is a WednesdayAI addition with no upstream equivalent.

An `upstream only` hook has one of two dispositions:

- `planned port` — a port into the WednesdayAI hook surface is planned and tracked.
- `unsupported` — there is no equivalent seam in WednesdayAI and no port is planned.

WednesdayAI ships no runtime aliases. Registering an upstream only name is never silently
remapped: if the map names a `Use instead` hook, the plugin must register that hook itself.

## When a hook is not dispatched

When a plugin registers an upstream only hook name with `api.on`, the handler is ignored and
the plugin keeps loading. The ignored registration is reported as a `PLUGIN_HOOK_NOT_DISPATCHED`
warning, so a plugin that relies on the handler silently does nothing while still appearing to
load.

Operators see the warning in four places:

- The gateway startup log, for example:

  ```
  [plugins] startup: 0 loaded, 1 warning — see warnings below
    ⚠ hook-ghost — unknown typed hook "before_agent_run" ignored: upstream openclaw hook not dispatched by WednesdayAI (unsupported; use "before_agent_start") (PLUGIN_HOOK_NOT_DISPATCHED)
      → See the hook parity map: https://docs.wednesdayai.dev/developers/plugins/hook-parity
  ```

- `wednesdayai plugins list` shows the plugin as `degraded`.
- `wednesdayai plugins status` lists the issue with its remediation.
- `wednesdayai plugins doctor` reports the same warnings.

The same rules apply to `api.registerHook`. A typed hook name belongs on `api.on`;
registering one through `registerHook` warns. An event string that no internal emitter
produces warns the same way. The event strings that core actually produces are listed in
[Internal hooks](/automation/hooks).

## Updating the map

Maintainers update the map when the upstream hook surface changes:

1. Copy the upstream hook names at the new tag from upstream `src/plugins/hook-types.ts`
   (the `PLUGIN_HOOK_NAMES` array at 2026.6.x, the `PLUGIN_HOOK_METADATA` keys at 2026.10.x)
   into `src/plugins/hook-parity.json` together with the new version, tag and commit.
2. Run `pnpm exec vitest run src/plugins/hook-parity.test.ts`. The test names every missing
   or stale disposition.
3. Fill in the dispositions in `src/plugins/hook-parity.json` and run `pnpm docs:hook-parity`
   to regenerate the table above.
4. Amend the compatibility ADR.
